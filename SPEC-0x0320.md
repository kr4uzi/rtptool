# RTPatch format version 0x0320

This supplements [SPEC.md](SPEC.md) and describes how version 0x0320 differs
from **the 0x0209 implementation in this repository**, rather than claiming that
every difference was introduced by 0x0320. No independent 0x0209 sample was
available for comparison, and some names in the older code appear to be
incomplete interpretations of the older format.

**Evidence.** Everything below was derived from one reference corpus: the four
0x0320 payloads of a commercial game's update, together with their RTD listing
files and an independently installed result of applying the update. The parser
and applier are deliberately restricted to the flags and layouts observed in
that corpus; anything else is rejected rather than interpreted. This document
is therefore a description of one well-tested variant, not an assertion about
every 0x0320 patch.

**Assessment.** 0x0320 is an extension of the same format family. The
compression codec and the diff opcode program model are unchanged. What differs
is container and application semantics: a shifted header, different record type
numbers, HISTORY records that group successive versions of one file, inherited
source descriptors inside such groups, and full-file ADD and DELETE records.
Raising the version ceiling alone is insufficient.

## Notation

All offsets are **relative to the start of the individual RTP payload**.
Fixed-width integers are little-endian; compressed bits are MSB first.
`string`, `VLI` and `entry` keep the encodings in SPEC.md, with entry details
clarified below.

| Payload | RTP bytes | Directories | Top-level records | HISTORY groups |
| --- | ---: | ---: | ---: | ---: |
| 1 | 510,227,636 | 155 | 394 | 161 |
| 2 | 26,305,147 | 14 | 21 | 9 |
| 3 | 1,114,267 | 7 | 13 | 0 |
| 4 | 19,531,077 | 71 | 108 | 51 |

Every payload ends with exactly `00 10` at `RTP size - 2`; there is no trailing
region.

## Header and directory table

The first twelve bytes of every payload in the corpus are:

```text
4b 2a 20 03 e4 b7 00 00 01 00 08 00
```

| Offset | Size | Observed field / interpretation |
| --- | ---: | --- |
| `0x00` | 2 | Magic `K*`, unchanged |
| `0x02` | 2 | Version `0x0320` |
| `0x04` | 2 | Flags `0xb7e4` |
| `0x06` | 4 | Extended flags `0x00010000`: extra-entry mode, low three bits zero |
| `0x0a` | 2 | Default record options `0x0008` |
| `0x0c` | 12 | Opaque, payload-dependent header region; semantics unresolved |
| `0x18` | 2 | Zero; position corresponding to old default attributes after the shift |
| `0x1a` | 2 | Zero, reserved/unknown |
| `0x1c` | 2 | Command flags `0x0004` |
| `0x1e` | 4 | Exactly the top-level file-record count |
| `0x22` | 4 | Constant `0x0acadc6b`, semantics unresolved |
| `0x26` | 2 | Directory-string count |
| `0x28` | variable | Directory strings |

The 0x0209 parser consumes **eight** bytes after the default options, naming
them `patch_total_size` and `reserved_a`. 0x0320 payloads need **twelve** before
the following zero words and command flags align. The insertion point and the
meaning of that region have not been established; in particular those bytes
cannot responsibly be exposed as a verified total size or checksum.

The word the old code calls `combine_mode_id` behaves like a count in all four
payloads (it equals the top-level record count). The command-bit gate and field
width match the existing code. Whether this field has other meanings in other
modes remains open.

The existing extended-flags and directory-table flag gates work. Extra-entry
mode is set in all four payloads; a non-extra 0x0320 variant is untested.
Directory strings use the same byte/u16 escaped length and final NUL
convention. They include both DOS 8.3 aliases and long paths, for example
directory 0 `admin\STANDA~1` and directory 1 `admin\standard_admin`. No
separately indexed file table was found: the records and history groups form
the file table.

## Top-level record framing and types

The **top-level** header remains a u16 with the type in bits 15–12, but the
type numbers differ from the enum used for 0x0209:

| Type | 0x0320 meaning | Existing 0x0209 enum name |
| --- | --- | --- |
| 1 | EOF | EOF |
| 2 | ADD, with compressed full file inline | RENAME |
| 3 | DELETE, with source descriptor(s), no inline data | NEW |
| 4 | MODIFY, compressed diff program inline | MODIFY |
| 5 | HISTORY, containing child operations | MKDIR |
| 6 | Not observed | DELETE |

The ADD/DELETE meanings were checked against the RTD listing rows that
accompany each payload. The HISTORY interpretation was checked by child counts,
exact byte spans, source/destination linkage and actual sequential application.
It is not safe to retain the 0x0209 enum meanings for these payloads.

Observed top-level header words are `0x2446`, `0x3444`, `0x3446`, `0x4444`,
`0x4446`, `0x5806`, and the EOF `0x1000`. Low-bit behavior retained from the
old parser includes bit 1 for an option override and bit 2 for the filename
string. The corpus never exercises the explicit path-pair bit 9, disk-index
bit 7 or attribute-override bit 8 at this level. Bit 10 is set on ordinary
operations; HISTORY has bit 11 set instead. Their full definitions remain open.

After the header:

1. Read an option override when bit 1 is set. Ordinary records store a u16;
   HISTORY has two additional zero bytes before the filename. The
   implementation treats the HISTORY override as a u32 under bit 11; the
   evidence cannot distinguish a u32 option field from a u16 followed by a
   separate zero u16.
2. Read the filename string when bit 2 is set. These are full relative target
   paths, not just basenames.
3. When the options intersect `0x00c0`, read two VLIs (extra-entry mode). All
   observed values are valid directory-table indices. Pairs such as `(0,1)`
   resolve to the DOS and long spellings of the same parent. The old names
   "seek" and "checksum" are misleading here; the exact distinction between the
   two directory roles is not proven. Use the full target path and the long
   entry name for portable lookup rather than depending on DOS alias generation.
4. HISTORY alone has a u32 child-region byte length and a u16 child count.
5. Read the ten-byte common metadata block, zero in every observed record.
6. Read the operation body, or the bounded HISTORY child region.

All effective ordinary/HISTORY options are `0x0008` or `0x01b8`. Flags beyond
the observed framing behavior, including the extra bits of `0x01b8`, should
remain explicit unknowns rather than invented feature names.

### Ordinary operation bodies

```text
MODIFY: u16 file_mod_flags, VLI source_count,
        VLI destination_count, u32 expanded_length, u32 compressed_length,
        source entries, destination entries, compressed bytes

ADD:    VLI destination_count, u32 expanded_length, u32 compressed_length,
        destination entries, compressed bytes

DELETE: VLI source_count, source entries; no compressed bytes
```

Every source/destination count in the corpus is one when present. Multiple
versions live in HISTORY chains; they must not be mistaken for simultaneous
multi-source opcode programs. `file_mod_flags` is `0x0009` or `0x000d`. Bit 2
cannot mean "size changes": in the corpus `0x0009` covers both same-size and
changed-size transitions, and so does `0x000d`. Its meaning is unresolved.

The field the old code calls `_unk4`, immediately before the compressed length,
is the **decompressed stream length**. For MODIFY this is the program length,
not the destination file size. For ADD it equals the full file length. Use it
to bound decompression and to verify completion, instead of the earlier
heuristic `max(destination_size * 4, 4 MiB)` with a silent output cap.

## HISTORY child framing and inheritance

A HISTORY body is exactly the declared byte span and contains exactly the
declared number of children, with no nested EOF. Children use a **different
header representation**: the operation type is in the **low nibble** of their
u16. They inherit the parent's pathname, options and context, and omit the
ten-byte top-level metadata block.

Observed child headers:

| Word | Body |
| --- | --- |
| `0x02c4` | MODIFY |
| `0x02c2` | ADD |
| `0x02c3` | DELETE |
| `0x0243` | Source metadata only; the RTD row still describes a historical MODIFY |

For the first child MODIFY, use the ordinary MODIFY body layout. For subsequent
child MODIFY operations, **omit `source_count`**, inherit one source descriptor
from the preceding child's destination, and read only a ten-byte source
checksum where the full source entry would otherwise appear. Destination count,
lengths, the full destination entry and the compressed bytes remain present. In
the corpus all 794 inherited source checksums equal the preceding destination
checksum exactly. Inherited metadata is scoped to a history group. No
simultaneous multiple-source case was observed.

Child ADD and DELETE use their ordinary body layouts, without a top-level record
prefix. Source-only `0x0243` uses the DELETE-shaped body. Eight occur in the
corpus, each followed by a terminal DELETE. Their RTD rows still describe
earlier MODIFY payload sizes, but those payloads are absent from the binary.
**Do not read those RTD sizes as byte spans.** The relationship of bit `0x0080`
to discarded versus active historical operations is inferred, not a complete
flag definition.

A concrete framing example from payload 1, an eleven-step history of a DLL:

- Parent at `0x1408`: header `06 58`, option/context prefix, filename, then
  child length 683,541, child count 11, and zero metadata.
- Child region begins at `0x1429`: `c4 02 0d 00 01 01`, followed by expanded
  length 190,756 and compressed length 97,913; full source/destination entries.
- Its compressed stream begins at `0x14a1`.
- The next child begins at `0x1931a`: `c4 02 0d 00 01`, followed by expanded
  length 114,347 and compressed length 54,208; source checksum only, full
  destination entry.
- Eleven children end exactly at `0xa823e`, the next top-level HISTORY header.

The children are **successive version transitions**. To apply a history, find
the step whose source size and checksums match the file at hand and apply the
remaining suffix; a file that already matches the final destination needs no
work. Histories may also begin with an ADD, contain a DELETE followed by an
ADD, or contain only a DELETE. Every starting point of a real five-step chain
was validated against the independent reference.

## Entry descriptors and checksums

The existing extra-mode entry layout works throughout:

```text
24-byte descriptor, 10-byte checksum, 8 timestamp bytes, string long basename
```

Within the 24-byte block, bytes 0–12 contain the NUL-terminated DOS basename
slot, attributes are at offset 14, the file size is a u32 at offset 16, and the
final four bytes are timestamp-like metadata. The extra eight timestamp bytes
are retained raw; creation/access/modification roles and high-bit conventions
have not been proven. The final string is a long **basename**, not an alternate
full directory path. Preserve both naming forms.

The ten-byte checksums retain `b0, b1, w1:u32, w2:u32`. All 2,362 source and
destination descriptors in the corpus, including inherited entries, satisfy:

```text
b0 = file_size mod 31
b1 = file_size mod 30
```

The existing 31/30-bit rotate-XOR algorithms validate actual sources,
intermediate destinations and final outputs. Mask the high reserved bit of
`w1` and the high two bits of `w2`, as the Rust code does. Validate the size
and both checksums before selecting a history suffix, and validate the
destination after each applied step. The old wrapper checked only the first
source's `w2` and never validated a destination.

No container-level integrity algorithm has been established for the opaque
header bytes. Entry rolling checksums are not cryptographic integrity checks;
compare against an independent reference when stronger evidence is needed.

## Compression and diff opcodes

All 1,167 compressed streams in the corpus share the same first 60 bits:

| Field | Value |
| --- | --- |
| Magic | `0xb59c` |
| Literal mode | 0, adaptive Huffman |
| Previously reserved byte | `0xff` |
| Initial period | 64 |
| Update period | 16 |
| Window selector | 8, the existing 8 KiB variant |

The common prefix is `b5 9c 00 ff 04 00 10 8…`. There is no observed DEFLATE,
zlib wrapper, encryption layer or new codec signature.

[tools/rtp0320_codec.py](tools/rtp0320_codec.py) is a readable reference
translation of the adaptive Huffman/LZSS decoder with a simpler bit-at-a-time
canonical decoder. It requires the distance-zero terminator, the exact declared
expanded length and fewer than eight residual padding bits; unlike the original
Rust decoder it does not treat reaching an output cap as success. ADD streams
decompress directly to full file bytes and must **not** pass through the opcode
interpreter.

MODIFY streams use the existing source selection, absolute COPY, gaps/FLUSH,
templates, fills and delta-poke program model (opcodes `0x01`–`0x16` in
src/apply.rs), executed with strict input/output bounds and an explicit END.
Every MODIFY program in the corpus passes framing and bounds checks; the corpus
never uses opcodes `0x06`, `0x07`, or `0x0e`–`0x10`, which are covered by
synthetic tests instead. All programs start with source selection zero. Both
flag variants `0x0009` and `0x000d` use the same decoder and program model.

## Implementation notes

The version branch in `src/parser.rs` retains the existing <=0x0209 mapping and
uses `src/parser0320.rs` for the extra-entry 0x0320 layout. The latter requires
known header/options/record words, single descriptors, bounded history
spans/counts, matching inherited **raw ten-byte** checksums, valid directory
indices, correct length accumulators, the declared top-level count, and an
exact EOF. Unknown header bytes, descriptor bytes, timestamp bytes, names and
options remain explicit metadata; the opaque header region is not presented as
a verified total size. Names in the corpus are ASCII; the strict path accepts
UTF-8 names and rejects other byte encodings rather than substituting.

`apply_record` takes an optional source and returns an optional destination.
It matches all checksum fields and the size once to select the latest matching
source transition, accepts already-final data, then validates each source and
destination of the remaining suffix. Absent data starts at the last applicable
ADD; this covers DELETE→ADD without pretending an unavailable historical source
was validated. Present unknown versions fail. Present DELETE sources must match;
already-absent terminal DELETE targets are accepted. Metadata-only records do
not perform the omitted historical transformation. The CLI never deletes input
files and reports failures rather than silently clipping copies or growing a
wrong-sized destination. It emits changes and deletions into a separate staging
tree; it does not simulate installer registry, feature selection or generated
files.

The exact decoder uses bounded canonical Huffman decoding, a required distance-
zero terminator, the exact expanded length and fewer than eight remaining
padding bits. ADD bypasses the diff interpreter. Strict MODIFY execution rejects
a missing END, trailing opcodes, unfilled literal gaps, invalid source/template
indices, and out-of-bounds COPY/fill/poke operations. The legacy
decoder/application path remains separate; only small synthetic legacy fixtures
were available for regression, so no independent real 0x0209 acceptance is
claimed.

Synthetic tests cover framing/inheritance/count/length failures,
ADD/DELETE/history selection, checksum failures, codec truncation/size/padding,
adaptive Huffman rebuilding and overlapping LZ matches, all opcode branches,
legacy parsing/application, and CLI protection of source files during DELETE.
Against the reference corpus, all 1,167 streams decode to their declared
lengths, all 148 ADD destinations pass both checksums, and the applied output
matched the independently installed reference byte for byte for every file the
corpus could produce from its base files.

## Remaining format questions

- Exact structure, insertion point and integrity semantics of header bytes
  `0x0c`–`0x17`; meaning of the final constant and of the command/count field
  in general.
- Exact meanings of top-level bits 10/11, child upper bits, extended HISTORY
  options, `0x0009` versus `0x000d`, and the `0x01b8` option bits.
- Source-descriptor inheritance and counts outside this all-single-source
  corpus; full semantics of the discarded historical MODIFY rows.
- Precise short/long directory-index roles, timestamp formats and attribute
  policy; rename/directory records and non-extra mode are absent from the
  corpus.
