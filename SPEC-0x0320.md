# RTPatch 0x0320: Battlefield 2 corpus notes

Analysis tag `rtp-0320`, 2026-11-10. This supplements [SPEC.md](SPEC.md) and
describes differences from **the implementation in this repository**, rather
than claiming that every difference was introduced by version 0x0320. No 0x0209
sample was supplied for an independent comparison. Some old names in the code
appear to be incomplete interpretations of the older format.

**Phase-2 status:** Rust support and the requested 125-path acceptance are now
implemented and validated; see the phase-2 results below. Phase-1 measurements
are retained as historical evidence.

**Assessment:** an extension of the same format family, with substantial missing
container/application semantics, rather than a replacement compression or diff
format. Raising the version ceiling alone is insufficient. A read-only Python
prototype parses all four supplied payloads, including every history child, to
exact EOF. Initial retail-disc MODIFY applications, including a five-step
history, reproduce the installed reference exactly. Rust was not changed
or built during phase 1; phase 2 implements the observed layout.

## Header and directory table

The first twelve bytes of every input are:

```text
4b 2a 20 03 e4 b7 00 00 01 00 08 00
```

| Offset | Size | Observed field / interpretation |
| --- | ---: | --- |
| `0x00` | 2 | Magic `K*`, unchanged |
| `0x02` | 2 | Version `0x0320` |
| `0x04` | 2 | Flags `0xb7e4` |
| `0x06` | 4 | Extended flags `0x00010000`: extra-entry mode, low three bits zero |
| `0x0a` | 2 | Default record options `0x0008` |
| `0x0c` | 12 | Opaque, product-dependent header region; semantics unresolved |
| `0x18` | 2 | Zero; position corresponding to old default attributes after the shift |
| `0x1a` | 2 | Zero, reserved/unknown |
| `0x1c` | 2 | Command flags `0x0004` |
| `0x1e` | 4 | 394 / 21 / 13 / 108: exactly the top-level file-record count |
| `0x22` | 4 | Constant `0x0acadc6b`, semantics unresolved |
| `0x26` | 2 | Directory-string count |
| `0x28` | variable | Directory strings |

The old parser consumes **eight** bytes after default options, naming them
`patch_total_size` and `reserved_a`. These inputs need **twelve** before the
following zero words and command flags align. This is an observed four-byte
layout difference; the insertion point and meaning within that region have not
been established. In particular, those bytes cannot responsibly be exposed as
a verified total size or checksum. For BF2 the twelve bytes are
`88 13 6b 4c 52 02 fd d0 ea 53 ac 87`.

The word currently called `combine_mode_id` has count-like behavior in all four
inputs. The command-bit gate and field width match the existing code. Whether
this field has other meanings in other modes remains open.

The existing extended-flags and directory-table flag gates work. Extra-entry
mode is set in all four files; a non-extra 0x0320 variant is untested. Directory
strings use the same byte/u16 escaped length and final NUL convention. They
include both DOS aliases and long paths, for example directory 0 is
`admin\STANDA~1` and directory 1 is `admin\standard_admin` in BF2.
The first top-level record starts at `0x1408`, `0x1df`, `0xe3`, and `0x9ac`
respectively. No separately indexed file table was found: the records and
history groups form the file table.

## Top-level record framing and types

The **top-level** header remains a u16 with type in bits 15–12.

| Type | Corpus meaning | Existing enum/name |
| --- | --- | --- |
| 1 | EOF | EOF |
| 2 | ADD, with compressed full file inline | RENAME |
| 3 | DELETE, with source descriptor(s), no inline data | NEW |
| 4 | MODIFY, compressed diff program inline | MODIFY |
| 5 | HISTORY, containing child operations | MKDIR |
| 6 | Not observed | DELETE |

The ADD/DELETE meanings are independently checked against the author-generated
RTD rows. The history interpretation is checked by child counts, exact byte
spans, source/destination linkage and actual sequential application. It is not
safe to retain the existing enum meanings for these inputs.

Observed top-level header words are `0x2446`, `0x3444`, `0x3446`, `0x4444`,
`0x4446`, `0x5806`, and the EOF `0x1000`. Low-bit behavior retained from the
old parser includes bit 1 for option override and bit 2 for the filename string.
The corpus never exercises explicit path-pair bit 9, disk-index bit 7 or
attribute-override bit 8 at this level. Bit 10 is set on ordinary operations;
HISTORY instead has bit 11 set. Their full semantic definitions remain open.

After the header:

1. Read an option override when bit 1 is set. Ordinary records store u16;
   HISTORY has two additional zero bytes before the filename. The prototype
   treats its override as u32 under bit 11. The evidence cannot distinguish a
   u32 option field from u16 options followed by a separate zero u16.
2. Read the filename string when bit 2 is set. These are full relative target
   paths, not just basenames.
3. When options intersect `0x00c0`, read two VLIs in this extra-entry mode.
   All their values are valid directory-table indices. Pairs such as `(0,1)`
   resolve to DOS/long spellings of the same parent. The old names “seek” and
   “checksum” are misleading here; the exact distinction between the two
   directory roles is not proven. Use the full target path and long entry name
   for portable lookup rather than depending on DOS alias generation.
4. HISTORY alone has a u32 child-region byte length and u16 child count.
5. Read the ten-byte common metadata block, zero in every top-level record.
6. Read the operation body, or the bounded HISTORY child region.

All effective ordinary/HISTORY options are `0x0008` or `0x01b8`. Flags beyond
the observed framing behavior, including the extra bits of `0x01b8`, should
remain explicit unknowns rather than invented feature names.

### Ordinary operation bodies

```text
MODIFY: u16 file_mod_flags, VLI source_count,
        VLI destination_count, u32 expanded_length, u32 compressed_length,
        source entries, destination entries, compressed bytes

ADD:    VLI destination_count, u32 expanded_length, u32 compressed_length,
        destination entries, compressed bytes

DELETE: VLI source_count, source entries; no compressed bytes
```

Every source/destination count in this corpus is one when present. Multiple
versions live in history chains; they must not be mistaken for simultaneous
multi-source opcode programs. `file_mod_flags` is `0x0009` or `0x000d`; the
meaning of their differing bit 2 has not been established.

The old `_unk4` immediately before compressed length is the **decompressed
stream length** in validated samples. For MODIFY this is program length, not
destination file size. For ADD it equals full file length. Use it to bound
decompression and verify completion rather than the Rust wrapper's current
heuristic `max(destination_size * 4, 4 MiB)` and silent output cap.

## HISTORY child framing and inheritance

A HISTORY body is exactly the declared byte span and contains exactly the
declared number of children, with no nested EOF. Children use a **different
header representation**: operation type is in the **low nibble** of their u16.
They inherit the parent's pathname/options/context and omit the ten-byte
top-level metadata block.

Observed child headers:

| Word | Body |
| --- | --- |
| `0x02c4` | MODIFY |
| `0x02c2` | ADD |
| `0x02c3` | DELETE |
| `0x0243` | Source metadata only; associated RTD row says historical MODIFY |

For an initial child MODIFY, use the ordinary MODIFY body layout. For subsequent
child MODIFY operations, **omit `source_count`**, inherit one source descriptor
from the preceding child's destination, and read only a ten-byte source checksum
where the full source entry would otherwise appear. Destination count, lengths,
full destination entry and compressed bytes remain present. All 794 such source
checksums exactly equal the preceding destination checksum. Inherited metadata
is scoped to a history group. No simultaneous multiple-source case was observed.

Child ADD and DELETE use their ordinary body layouts, without a top-level
record prefix. Source-only `0x0243` uses the DELETE-shaped body. Seven occur in
BF2 and one in XP1, each followed by a terminal DELETE. Their corresponding RTD
rows still describe earlier MODIFY payload sizes, but those payloads are absent
from the binary. **Do not read those RTD sizes as byte spans.** The relationship
of bit `0x0080` to discarded/active historical operations is inferred, not a
complete flag definition.

BF2 `AIDLL.dll` is a concrete framing example:

- Parent at `0x1408`: header `06 58`, option/context prefix, filename, then
  child length 683,541, child count 11, and zero metadata.
- Child region begins at `0x1429`: `c4 02 0d 00 01 01`, followed by expanded
  length 190,756 and compressed length 97,913; full source/destination entries.
- Its compressed stream begins at `0x14a1`.
- Next child begins at `0x1931a`: `c4 02 0d 00 01`, followed by expanded length
  114,347 and compressed length 54,208; source checksum only, full destination.
- Eleven children end exactly at `0xa823e`, the next top-level HISTORY header.

These are **successive version transitions**. Apply the chain from a source
whose size/checksums match a particular step, through its remaining suffix.
The five autobalance transitions were validated from the retail source through
to the installed result. Phase 2 also validates every starting point of that real five-step chain and
detects its already-final output. Histories may
also begin with ADD, contain DELETE followed by ADD, or contain only a DELETE.

## Entry descriptors and checksums

The existing extra-mode entry layout works throughout:

```text
24-byte descriptor, 10-byte checksum, 8 timestamp bytes, string long basename
```

Within the 24-byte block, bytes 0–12 contain the NUL-terminated DOS/basename
slot, attributes are at offset 14, file size is u32 at offset 16, and the final
four bytes are timestamp-like metadata. The extra eight timestamp bytes are
retained raw; creation/access/modification roles and high-bit conventions have
not been proven. The final string is a long **basename** in this corpus,
not an alternate full directory path. Preserve both naming forms.

The ten-byte checksums retain `b0, b1, w1:u32, w2:u32`. All 2,362 source and
destination descriptors, including inherited entries, satisfy:

```text
b0 = file_size mod 31
b1 = file_size mod 30
```

The old 31/30-bit rotate-XOR algorithms also validate actual sample sources,
intermediate destinations and final outputs. Mask the high reserved bit of
`w1` and high two bits of `w2`, as the Rust code does. Validate size and both
checksums before selecting a history suffix, and validate the destination after
each applied step. The old wrapper checks only the first source's `w2` and
does not validate a destination.

No container-level integrity algorithm has been established for the opaque
header bytes. Entry rolling checksums are not cryptographic integrity checks;
SHA-256 comparisons to the independent installed files supply stronger local
validation evidence.

## Compression and diff opcodes

All **1,167** compressed streams have the same first 60 bits:

| Field | Value |
| --- | --- |
| Magic | `0xb59c` |
| Literal mode | 0, adaptive Huffman |
| Previously reserved byte | `0xff` |
| Initial period | 64 |
| Update period | 16 |
| Window selector | 8, existing 8 KiB variant |

The common prefix is `b5 9c 00 ff 04 00 10 8…`. There is no observed DEFLATE,
zlib wrapper, encryption layer or new codec signature in the RTP data. The
separate InstallShield cabinet reader does use raw DEFLATE for disc files.

[tools/rtp0320_codec.py](tools/rtp0320_codec.py) translates the existing adaptive
Huffman/LZSS implementation and uses a simpler bit-at-a-time canonical decoder.
It requires the distance-zero terminator, exact declared expanded length and
fewer than eight residual padding bits. Unlike the existing Rust decoder, it
does not treat reaching an output cap as success. ADD streams decompress
directly to full file bytes and must **not** pass through the opcode interpreter.

MODIFY streams use the existing source selection, absolute COPY, gaps/FLUSH,
templates, fills and delta-poke program model. The prototype implements opcodes
`0x01`–`0x16` from src/apply.rs with strict input/output bounds and explicit END.
Actual retail-disc samples validate COPY, gap insertion, literal flush and
template copies without changing those semantics. Syntax checks additionally
exercise template reuse, zero fill, variable one-byte pokes and 1/2/4-byte
pattern fills, including gap variants. Opcodes `0x06`, `0x07`, and `0x0e`–`0x10`
were not exercised. No new opcode has yet been required. Phase 2 additionally decodes every large stream and checks every MODIFY
program against declared source/destination bounds; see the results below.

## Reproduction and measured validation

The prototype writes **no reconstructed files**. Source cabinet files, decoded
programs and final bytes are held in memory and discarded. It reads both the
source and reference read-only. It imports the owner's existing installer
reader rather than vendoring unrelated installer code. Run from this worktree:

```sh
python3 tools/rtp0320.py \
  --sfx '/path/to/BF2 Patch v. 1.0 - v. 1.41.exe' \
  --installer-reader /path/to/installer/formats.py \
  --decode-limit 65536 \
  --verify-samples \
  --iso '/path/to/BF2 Image.iso' \
  --installed '/path/to/installed/Battlefield 2'
```

Without optional flags it performs complete structural parsing and RTD
cross-checking. `--json` prints the metadata inventory. `--decode-limit` fully
decodes streams whose declared expanded length fits the threshold, validates
ADD destination checksums, and syntax/bounds-checks MODIFY programs with a zero
source when source/destination sizes are at most 2 MiB. That last check is not
a content-validation claim. `--verify-samples` performs actual disc-source
application for four named files and checks two additional full-file additions.

The 65,536-byte threshold run completed successfully:

## Original Rust phase 2 plan and effort (completed for the observed corpus)

1. Add an explicit 0x0320 parsing branch in src/parser.rs and types in
   src/types.rs. Preserve the 0x0209 behavior until independent regression
   samples distinguish an old-spec error from a version-specific change.
   Represent header unknowns, directory references, declared expanded sizes,
   history groups, inherited descriptors and ADD/DELETE meanings explicitly.
   Require exact child spans/counts and EOF; reject unknown combinations.
2. Reuse src/codec.rs, adding exact expanded-length, terminator and range checks.
   Separate “decode full ADD file” from “decode MODIFY program.” Retain the
   opcode engine, tightening bounds/END handling and validating both checksums.
   Resolve any new behavior found by full decoding before advertising support.
3. Add library/CLI history selection and suffix application. Match the source
   by size/checksums, detect an already-final file, preserve the full pathname,
   process ADD and DELETE, and keep output in a separate staging tree. Respect
   optional expansion/booster inputs; do not turn absent base media into a
   successful installation. Avoid the current permissive copy clipping/growing
   behavior masking an incorrect record selection.
4. Use synthetic, redistributable framing/opcode fixtures in tests. Keep owner
   media as opt-in local integration inputs. Decode all streams, apply retail
   disc → 1.41, overlay full 1.50 files, then compare the exact 125-path gap set
   byte-for-byte against the reference. Track any used-installation deviations
   separately. No game payload belongs in Git fixtures.

Original planning estimate after Rust was available: **3–6 engineering days** for parser/model work,
history/ADD/DELETE integration and local corpus acceptance, assuming large-stream
decoding confirms the reused codec/opcode engine. Unexplained header integrity
fields, unusual historical records or additional stream behavior could extend
that estimate. A parser-only version bump is much smaller but would not fulfill
the installation goal.

## Phase 2: Rust implementation and measured acceptance

The version branch in `src/parser.rs` retains the existing <=0x0209 mapping and
uses `src/parser0320.rs` for the observed extra-entry 0x0320 layout. The latter
requires known header/options/record words, single descriptors, bounded history
spans/counts, matching inherited **raw ten-byte** checksums, directory indices,
length accumulators, the declared top-level count, and exact EOF. Unknown header
bytes, descriptor bytes, timestamp bytes, names and options remain explicit
metadata; the opaque header region is not presented as a verified total size.
Names in the supplied corpus are ASCII. The strict path currently accepts UTF-8
names and rejects other byte encodings rather than silently substituting names.

`apply_record` takes an optional source and returns an optional destination.
It matches all checksum fields and size once to select the latest matching
source transition, accepts already-final data, then validates each source and
destination of the remaining suffix. Absent data starts at the last applicable
ADD; this covers DELETE→ADD without pretending an unavailable historical source
was validated. Present unknown versions fail. Present DELETE sources must match;
already-absent terminal DELETE targets are accepted. Metadata-only records do
not perform the omitted historical transformation. The CLI never deletes input
files and reports failures rather than silently clipping copies or growing a
wrong-sized destination. It emits changes/deletions into a separate staging tree;
it does not simulate installer registry, feature selection or generated files.

The exact decoder uses bounded canonical Huffman decoding, a required distance-
zero terminator, exact expanded length and less than eight remaining padding
bits. ADD bypasses the diff interpreter. Strict MODIFY execution rejects missing
END, trailing opcodes, unfilled literal gaps, invalid source/template indices,
and out-of-bounds COPY/fill/poke operations. The legacy decoder/application path
remains separate. Only small synthetic legacy fixtures were available for
regression; no independent real 0x0209 acceptance is claimed.

All streams, including the 200 formerly unchecked large bodies, were decoded:

| Product | Streams decoded | Expanded bytes | ADD checksum matches | MODIFY programs syntax/bounds checked |
| --- | ---: | ---: | ---: | ---: |
| bf2 | 879 | 502,997,681 | 123 | 756 |
| bp1 | 55 | 23,985,357 | 3 | 52 |
| bp2 | 13 | 1,022,625 | 0 | 13 |
| xp1 | 220 | 21,872,990 | 22 | 198 |
| Total | 1,167 | 549,878,653 | 148 | 1,019 |

The syntax check executes with synthetic zero source bytes of the declared size;
it proves program framing/bounds, not content for an unavailable historical
source. All actual application outputs are separately checksum-validated. No new
codec or opcode was needed. Corpus programs still never use `0x06`, `0x07`, or
`0x0e`–`0x10`; synthetic tests cover these branches and the fill/gap/template
variants. All programs start with source selection zero. Both flag variants
`0x0009` and `0x000d` use the same decoder and program model successfully.

The inputs do not justify more flag names. In particular bit 2 of the MODIFY
flags cannot mean "size changes": `0x0009` has 154 same-size and 96 changed-size
transitions, while `0x000d` has 402 same-size and 367 changed-size transitions.
Child bit `0x0080` distinguishes active `0x02c3` from source-only `0x0243` in the
eight observed discarded histories; its general meaning remains unproven.
The header integrity region, `0x01b8` option bits, and the two directory roles
remain unresolved. Reading all larger bodies does not add independent evidence
for these container flag meanings.

### Acceptance and reproduction

documented in README. It skips when inputs are absent. The harness imports the
OpenBF2 probe's reader and destination mapper, reads the ISO cabinet sources,
and verifies cabinet size/MD5 while extracting into the authorized scratch root.
It extracts the four RTP payloads from the read-only SFX, runs the Rust decoder
on all streams, attempts all records, overlays all **274** full 1.50 files and
compares bytes against the installed folder. It derives and cross-checks the
exact **125-path** report set (existing ADD/MODIFY targets without full 1.50
replacements; a DELETE-only UserSettings.con is excluded by the original probe).
No installed-reference data is used as patch input.

**Acceptance: 125 matched, 0 mismatched, 0 cannot be produced.** This includes
all large ZIP files in the stated set. Logs and generated bytes are outside Git,
under the scratch directory recorded in BF2-0x0320-PROGRESS.md.

## Remaining format questions

- Exact structure, insertion point and integrity semantics of header bytes
  `0x0c`–`0x17`; meaning of the final constant and command/count field generally.
- Exact meanings of top-level bits 10/11, child upper bits, extended HISTORY
  options, `0x0009` versus `0x000d`, and `0x01b8` option bits.
- Generalized source-descriptor inheritance and counts outside this all-single-
  source corpus; full semantics of the eight discarded historical MODIFY rows.
- Precise short/long directory-index roles, timestamp formats and attribute
  policy; rename/directory records and non-extra mode are absent from this set.
- Every historical source version outside the selected real chain, and complete
  optional-product installation acceptance. All large streams/program bounds and
  the 125-path acceptance now pass; absent expansion media still prevents full
  XP1 source-content checks.
